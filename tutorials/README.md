## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/t5_small_text2text_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 7-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/t5_small_text2text_input_manifest.json` with the schema, ceilings, each input's character count and `known_prefix` (an input with no trained prefix is recorded, not rejected — the pipeline does not refuse it either), the settings in force, the verdict and one recorded rejection finding (an out-of-range `num_beams`); `evaluation_report` (EVAL21) writes `outputs/t5_small_text2text_evaluation_report.json`: ROUGE-1/2/L F1 of the 20 referenced SciTLDR-A summaries beside the Lead-1 baseline, verdict `sample-sanity` (T5S-M1); the Section 4 inputs get `outputs/t5_small_text2text_inputs_evaluation_report.json`, `not-measurable` for the authored inputs (no references) and scored the same way for a BYOD CSV with references.
- The notebook exercises `T5SmallText2TextPipeline` carried verbatim in the notebook rather than reimplementing model loading; model acquisition goes through the package: `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries a fresh clone lacks (the git-ignored `model.safetensors`), at the pinned revision, `verify_snapshot` re-hashes every entry, and `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files (`local_files_only=True`, `trust_remote_code=False`); no cell outside the carried module calls `huggingface_hub` or `transformers`.
- The default sample is synthetic: two already-prefixed inputs authored in code (the card-pass smoke's `translate English to German: The house is wonderful.` and a four-sentence `summarize: ` passage); the pipeline invents no prefix and the notebook says so. These two have no reference outputs and are not scored; measurement uses the separate digest-pinned SciTLDR-A sample (abstract → human one-sentence summaries), and translation is scored only on BYOD references.
- Decision rule and score semantics: greedy per-step argmax (`num_beams=1`, `do_sample=False`) stated as the default, beam search as the alternative; the pipeline emits no probability or confidence and ships no acceptance threshold — the caller owns it. `stopped_by == 'max_new_tokens'` is explained as a truncated output.
- Ceilings `MAX_TEXT_CHARS` (20000), `MAX_INPUT_TOKENS` (512, rejected not truncated), `MAX_NEW_TOKENS` (512), `MAX_NUM_BEAMS` (8), `DEFAULT_MAX_NEW_TOKENS` (64), `DECISION_RULE` and `TASK_PREFIXES` are printed before the model runs; instruction following, sampling, batching, other language pairs and the upstream `task_specific_params` are named as out of scope.
- CPU is documented as adequate with the card-measured smoke numbers (3.89 s load + verify, 0.16 s / 0.31 s per call on an Intel Core Ultra 9 275HX).
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- Guided layer (NOTEBOOK_SPEC 2.2 §25.13, T5S-M3): How to use, Input → Model → Output table, roadmap, glossary, predictions with collapsed sample answers, a Predict → Change → Run → Observe → Explain activity (`NUM_BEAMS = 4`), troubleshooting table and conclusion template; Sections 1–3 are labelled Infrastructure and collapsed (`cellView: form`).
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
